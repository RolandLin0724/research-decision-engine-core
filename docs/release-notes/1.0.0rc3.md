## What RDE Core is

RDE Core is a local Python research core for bounded, sequential experiment
selection over a finite, ordered candidate set. It combines deterministic built-in
policies, trusted local workload adapters, SQLite-backed history, interruption and
resume, and portable RunBundles that can be verified and replayed.

Core is a research execution and artifact-compatibility boundary. It does not prove
scientific correctness, reproduce an external execution environment, establish
production readiness, or create authority or approval for the separately governed
RDE Assurance track.

## Highlights

- Executes bounded experiments over a finite candidate set.
- Supports `PythonFunctionAdapter` and `CommandAdapter` for trusted local
  workloads.
- Provides the `random`, `greedy_prior`, and `information_gain_table` policies in
  their supported schema versions.
- Persists completed execution history in local SQLite.
- Supports interruption and deterministic resume from completed history.
- Exports and verifies versioned RunBundles.
- Replays the decision process from recorded observations without executing the
  workload again.
- Provides semantically paired English and Simplified Chinese user documentation.
- Exercises the Core contract in Windows and Linux CI on CPython 3.12.
- Uses the Apache-2.0 license.

## Upgrade and SQLite migration notes

The historical package version described by these notes is `1.0.0rc3`. RunSpec and
RunBundle artifacts are not rewritten or silently converted. Historical canonical
RunBundle fixtures retain their `0.1.0` producer identity, while RC3-generated
bundles record `1.0.0rc3`. The active private candidate is now `1.0.0rc5`, and newly
generated bundles from it record `1.0.0rc5`; use the API that matches artifact v1,
v2, or v3 exactly.

A newly initialized database uses SQLite schema v6. Supported legacy schemas v1
through v5 advance one version at a time to v6. Each migration edge is atomic and
resumable: a failed current edge rolls back to its source state, while earlier
committed edges remain committed, and a later retry resumes at the last committed
version. Unknown future schemas fail closed before mutation. Downgrade is not
supported. Back up important databases before migration.

## RunBundle verification and replay behavior

RunBundle verification is read-only and fail-closed. It checks the closed canonical
schema, version and policy bindings, identity-bearing sections, the SHA-256 sidecar,
decision and rationale consistency, ordered candidate identities, producer-metadata
shape, and source identity and ancestry constraints. These integrity checks detect
tampering; they are not a digital signature, signer identity, third-party
attestation, or scientific validation.

Replay is version-matched for v1, v2, and v3. It uses the recorded observations to
recompute and compare the deterministic Core decisions, rationales, terminal
summary, and applicable belief lineage, then rebuilds fresh SQLite state. Replay
receives no workload adapter, callable, command builder, command, or plugin and does
not execute them. Arbitrary import-path, registry, URL, or plugin loading is not
supported. Replay does not recreate the original operating system, Python
environment, executable, dependencies, files, services, hardware, or other external
state.

## Security and trust boundaries

- `PythonFunctionAdapter` runs a user-provided callable in the current Python
  process. `CommandAdapter` starts a local child process with the current user's
  permissions. Both require trusted code.
- Neither adapter is a malicious-code sandbox, container, secret manager, or
  security-isolation boundary.
- RunSpecs, SQLite databases, command output, and RunBundles may contain
  user-provided data. Users must keep secrets out of those surfaces and sanitize
  artifacts before sharing them.
- Replay's non-execution boundary does not attest that the original workload or its
  observations were truthful.
- Bilingual security policies and a privacy/secret public-release gate are present,
  but that public-release gate is not complete.
- RDE Core results create no RDE Assurance authority, approval, review seal, or
  scientific attestation.

## Known limitations

- This is pre-release software; no public Core v1.0 or RC release exists.
- Only CPython 3.12 is supported (`>=3.12,<3.13`).
- Workloads run inside a trusted local process boundary.
- There is no malicious-code sandbox.
- No GPU is required, and no GPU executor is provided.
- No cluster executor is provided.
- No Web UI is provided.
- Continual Learning is not included in RDE Core.
- Core creates no RDE Assurance approval.
- Replay does not recreate the original external environment.
- The `information_gain_table` likelihood model is user-declared; Core does not
  learn or scientifically validate that model.
- No production-readiness claim is made.

## Feedback expectations for a future RC

Future RC feedback should identify the exact artifact or API version and include a
minimal sanitized reproduction. The most useful areas are public-API compatibility,
RunSpec/RunBundle version handling, verification or replay mismatches, SQLite
migration and resume behavior, Windows/Linux portability, adapter error behavior,
and discrepancies between the English and Simplified Chinese documentation.

Do not include credentials, private databases, private RunBundles, or unsanitized
user data in a report. Until an authorized future reporting channel exists, follow
the private repository's established maintainer process and the security policy;
do not use a public issue for a suspected vulnerability.
